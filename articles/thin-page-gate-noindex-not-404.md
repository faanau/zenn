運営しているサイトの145URLを調べたら、**37本が300語未満**だった。全体の26%。

そのうち27本は、テンプレートに埋め込まれたこの文言を本番に出していた。

```
Stub page — the production article includes first-appearance citation,
related terms, and panel references.
```

「本番の記事にはこれこれが含まれます」と本番で言っている。

## なぜ空箱が出ていたのか

書き手の怠慢ではなかった。**スキーマに本文を入れるフィールドが無かった。**

```ts
const glossary = defineCollection({
  schema: z.object({
    slug: z.string(),
    characterSlug: z.string(),
    term: z.string(),
    jp: z.string(),
    short: z.string(),      // 1〜2文の定義
    ...publishingFields,
  }),
});
```

`short` は定義文で、記事本文ではない。出典フィールドも、画像フィールドも無い。テンプレートは「本文が無い」前提で、あのプレースホルダを出すよう書かれていた。

つまり**書こうと思っても置き場所が無かった**。これに気づかず「記事を書き上げる」タスクとして扱っていたら、書いた本文をどこかに仮置きして忘れる展開になっていた。

まずスキーマを直した。ここは普通の作業なので省く。

## 個別に直しても再発する

37本を書き上げれば当面は解決する。だが**キャラを1人追加するたびに同じ状態が生まれる**。新しいキャラのglossaryは最初空で、それが本番に出る。

なので、ビルドに入れることにした。

## 404 ではなく noindex にする

最初に考えたのは「閾値未満はビルドから除外する」だった。既に `noindex: true` というフィールドがあり、それはまさにビルド除外（=404）として実装されていた。

**これは誤りだと判断した。**

薄いページに404を返すと、こうなる。

- Google が既に知っているURLがあり、それが突然404になる
- 内部リンクが張られている（一覧ページ、記事中の相互参照）
- そもそも**作業中の正当なページ**であって、消えたわけではない

`noindex, follow` の方が事実をそのまま表す。

> **まだインデックスに値しないが、リンクは辿ってよい**

だから既存の `noindex`（ハード除外・退役用）とは**別の仕組み**にした。

| | 既存の `noindex: true` | 新しい depth ゲート |
|---|---|---|
| 用途 | 退役（重複記事の統合など） | 未完成 |
| ビルド | 除外 | **される** |
| HTTP | 404（+CloudFrontで301） | **200** |
| robots | — | `noindex, follow` |
| sitemap | 出ない | 出ない |
| 内部リンク | 切れる | **生きている** |

実装は素朴だ。

```ts
export function isThin(entry: unknown): boolean {
  const data = (entry as any)?.data ?? entry;
  if (!data || typeof data !== 'object') return true;
  return proseWords(data) < CONTENT_DEPTH_MIN;
}

/** sitemap 用: 提出に値するものだけ残す */
export function indexable<T>(entries: T[]): T[] {
  return entries.filter((e) => !isThin(e));
}
```

テンプレート側は1行。

```astro
<SubPageShell noindex={isThin(entry)} ... >
```

sitemap 側も1行。

```ts
const [wisdom, pitfalls, gems] = (await Promise.all([...])).map(indexable);
```

**書き上げれば自動で sitemap に戻る。** 手動で何かを外したり戻したりする必要が無い。

## 語数の数え方

出典リストやメタデータで嵩増しできないようにする。

```ts
const NON_PROSE = new Set([
  'slug', 'characterSlug', 'sources', 'references',
  'seoTitle', 'supersededBy', 'mangaPanelJp', 'mangaPanelEn',
  'seedRef', 'tags', 'aiModel',
]);
```

これを除いて再帰的に数える。**引用文献を10件足しても閾値は超えない。**

## 閾値を「理想」に合わせると正常なものが死ぬ

ここがいちばん学びがあった。

執筆仕様では **800語以上**を求めている。だから最初 `CONTENT_DEPTH_MIN = 800` にした。

測ってから気づいた。

| リポジトリ | 800語で落ちる数 | 内訳 |
|---|---|---|
| 新しい方 | 80件中28件 | stub 26 + 本当に短い2 |
| 古い方 | **800語超えが3件しかない** | 実記事16本が巻き添え |

古い方は記事の書き方が違い、本文がJSONの粒度フィールドに分散していて、prose word count では800に届かない。**しかも巻き添えの中に、YouTubeパイロットの題材2本が含まれていた。**

インデックスを取ろうとしている最中に、完成済みの記事を非公開にすることになる。

なので分けた。

```
ゲートの閾値 = 300語（= stub の線）
執筆仕様     = 800語（レビューで担保）
```

**ゲートは「明らかな空箱」を止めるためのもので、「理想に達していないもの」を止めるためのものではない。** この2つを混同すると、正常なコンテンツを殺す。

コード上もそう書いた。

```ts
/**
 * THRESHOLD: 300 prose words — the STUB line, not the authoring target.
 *
 * 800 でゲートすると、片方のリポジトリで実記事16本が落ちる。うち2本は
 * YouTubeパイロットの題材。インデックスを取ろうとしている最中に
 * 完成済みの記事を非公開にするのは筋が悪い。
 *
 * RATCHET: バックログが減るごとに上げる（300 → 500 → 800）。
 * 上げる前に必ず犠牲になる記事を確認すること:
 *   CONTENT_DEPTH_MIN=500 npm run build && npm run check:apex-urls
 * 数字を良く見せるために下げてはいけない。
 */
```

**ラチェット**として設計するのが要点だと思う。最初から理想値を入れるのではなく、実態に合わせて始めて、バックログが減るごとに上げる。環境変数で上書きできるようにしておけば、上げる前に犠牲を確認できる。

## 結果

```
デプロイ前  live 139 URL（うち37本が300語未満）
デプロイ後  live 101 URL
```

**38本減ったが、これは後退ではない。** ページは全て200で生きていて、内部リンクも辿れる。提出をやめただけだ。

その後、書き上げが進んで **123 URL** に戻った。手動操作は一切していない。

```
/c/luffy/glossary/haki/   18語 → 1459語   noindex → index,follow
```

## GSCの見え方には注意

sitemap の登録件数が減るので、Search Console 上は「38件減った」ように見える。**意図した変更だと分かっていないと不安になる数字**なので、チームでやるなら事前に共有した方がいい。

## まとめ

- **空箱が出る原因が「書いていない」とは限らない。** スキーマに置き場所が無いこともある
- 未完成ページは **404 ではなく `noindex, follow`**。「まだ価値がないが、リンクは辿ってよい」が事実
- 退役（消す）と未完成（まだ）は**別の仕組みにする**。挙動が正反対
- 語数はメタデータを除いて数える。**引用で嵩増しできないように**
- **ゲートの閾値と執筆の目標は別物。** 理想値でゲートすると正常なものが死ぬ
- ラチェットとして設計し、上げる前に犠牲を確認する

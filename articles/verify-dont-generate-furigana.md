漫画の日本語を英語圏の学習者向けに解説するサイトを運営している。全記事の日本語原文にふりがなが付いている。

形態素解析器（kuromoji）を導入するとき、当然こう考えた。**ふりがなを自動生成しよう。**

実際にデータを見たら、前提が間違っていた。

```
59エントリ中、ふりがなあり: 59
```

**全部すでに付いていた。** 生成する対象が無い。

## 危険なのは欠落ではなく誤り

では解析器は不要かというと、そんなことはなかった。考えるべきは**何が実際にリスクか**だ。

ふりがなが「無い」ことは、ページを見ればすぐ分かる。目立つ。誰かが気づく。

ふりがなが「間違っている」ことは、**見ても分からない**。日本語ネイティブでも、読み間違いは一見して自然に見える。そして間違った読みは記事本文、PDF、動画台本へとそのまま伝播する。

うちのプロジェクトのレビュー記録には、実際にこの種の失敗が名指しで残っていた。

```
mattō ⇄ zennō
mori-en ⇄ seien
oni-koroshi-tai ⇄ kisatsutai
```

**生成ではなく検証に使うべきだった。**

## 3種類の検査

書いたチェッカーは3つのことを見る。順序は「どれだけ白黒つくか」で決めた。

### 1. カバー範囲

ふりがなは ruby マークアップで保存してある。

```html
お<ruby>前<rt>まえ</rt></ruby>は
```

ここから **ルビを剥がした表層** を再構成すると、元の行と一致するはずだ。

```js
function surfaceFromFurigana(furigana) {
  return furigana
    .replace(/<ruby>(.*?)<rt>.*?<\/rt><\/ruby>/g, (_m, base) => base)
    .replace(/<rp>.*?<\/rp>/g, '')
    .replace(/<[^>]+>/g, '');
}
```

一致しなければ、**ふりがなが行の一部しかカバーしていない**。これは議論の余地なく欠陥で、読者から見ると前半だけルビが付いて後半は素のまま、という状態になる。

3件見つかった。

```
jp   : あいつはこのオレが認めた優秀な生徒だ．．．あいつは木ノ葉隠れの里の．．．うずまきナルトだ
ruby : あいつはこのオレが認めた優秀な生徒だ            ← ここで止まっている
```

```
jp   : バーカ！！うっせんだってばよ！！
ruby : だってばよ                                    ← 断片だけ
```

```
jp   : 無理な話だ鬼が人を喰らう限りは
ruby : 無理な話だ鬼が人を喰う限りは                    ← 喰らう が 喰う になっている
```

3つ目は`<ruby>喰<rt>くら</rt></ruby>う` と書かれていた。読みは正しいが、送り仮名の `ら` が表層から消えている。**読みだけ見ていたら気づかない**種類の誤りだ。

比較の前に句読点は落とす。末尾の `！！` や `．．．` をルビ外に置くのは書式の選択であって、注釈漏れではない。ここを厳密にすると本物の欠陥がノイズに埋もれる。

### 2. 未注釈の漢字

範囲が一致していても、その中にルビの無い漢字が残っていることがある。

```js
function unannotatedKanji(furigana) {
  const outsideRuby = furigana
    .replace(/<ruby>.*?<\/ruby>/g, '')
    .replace(/<[^>]+>/g, '');
  return [...new Set(outsideRuby.match(/[一-龯々]/g) || [])];
}
```

**英語圏の学習者向けサイトでは、これが本質的な欠陥になる。** 読めない文字にこそ読みが要るのに、そこだけ抜けている。

1件見つかった。

```
jp   : 俺は頭にきてる
ruby : 俺は<ruby>頭<rt>あたま</rt></ruby>にきてる    ← 俺 にルビが無い
```

### 3. 読みの相違

ここでようやく解析器を使う。ruby から再構成した読みと、解析器が原文から導く読みを比べる。

```js
const claimed = kanaOnly(readingFromFurigana(furigana));
const derived = kanaOnly(
  tokenizer.tokenize(jp).map(t => t.reading || t.surface_form).join('')
);
```

12件が食い違った。

## そして12件すべて、辞書の方が間違っていた

これが本題だ。

| 語 | 著者 | IPADIC |
|---|---|---|
| 錆兎 | さびと | さび**うさぎ** |
| 冨岡義勇 | とみおかぎゆう | とみおか**よしたけ** |
| 鬼殺隊 | きさつたい | **おにやたい** |
| 拾壱 | じゅういち | **じついち** |
| 宝物 | たからもの | **ほうもつ** |
| 七日間 | なのかかん | **なにちかん** |
| 忍 | しのび | **にん** |
| 何の | なんの | **なにの** |
| 他の | ほかの | **たの** |
| 怒れ | いかれ | おこれ |

固有名詞は当然としても、`鬼殺隊 → おにやたい` のような分解由来の誤りや、`宝物 → ほうもつ`（作品中は「たからもの」）のような文脈依存の読みも混ざる。`怒れ` は「いかれ / おこれ」どちらも正しく、作品が採っている方を著者が選んでいる。

**IPADIC は一般語の辞書であって、作品固有の読みを知らない。** 当たり前だが、自動修正を実装する前に気づけて良かった。

## だから自動修正はしない

ここが設計上いちばん大事な判断だった。

```
✗ 解析器の読みで上書きする
✓ 食い違いを報告し、人間が答える
```

自動修正していたら、**正しい読みが12箇所壊れていた**。しかも壊れたことは見て分からない。

代わりに、レビュー済みの相違を理由付きで記録する仕組みにした。

```json
{
  "i-wont-manifest-the-mark":
    "錆兎 is the character Sabito. IPADIC has no entry and falls back to
     さびうさぎ ('rust rabbit').",
  "no-place-in-the-corps":
    "鬼殺隊 read きさつたい. IPADIC's おにやたい is a decomposition
     artifact. This is the exact kisatsutai ⇄ oni-koroshi-tai confusion
     the project's review notes call out."
}
```

キーは記事のスラッグ、値は**なぜ著者の読みが正しいのか**。単に「無視する」リストにしないのが要点で、こう書いておくと後から判断そのものを再検討できる。エントリを削れば、次回の実行でまた問いとして浮上する。

結果、日常の実行はこうなる。

```
$ npm run check:readings
readings — 55 checked, 4 with no ruby, 12 reviewed
  every authored reading agrees with the analyzer
```

**新しい相違が出たときだけ声が上がる。** 既知の12件は黙っている。

## 一般化：AI や辞書の出力をどう扱うか

同じ構図は、LLM の出力を検証するときにもそのまま出てくる。

- **生成器の出力を正解として上書きする** → 生成器が間違っている領域で、静かに品質が落ちる
- **生成器を検証器として使い、食い違いを人に見せる** → 生成器が間違っていても害が無い

この2つは実装コストがほとんど変わらないのに、**失敗したときの挙動が正反対**になる。前者は誤りを増やし、後者は誤りを見つける。

そして「食い違いは問いであって判定ではない」という前提を、コードとドキュメントの両方に書いておく。書いておかないと、次に触る人が良かれと思って自動修正を実装する。私が最初にそうしかけた。

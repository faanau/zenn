新しいドメインで始めた事業サイトが、いつまでもインデックスされない。全URLを調べたら、151本中133本を Google が**存在すら知らなかった**。

このとき私は「リンクの関連性が薄いから効かない」という説明をしていた。法人サイトから事業サイトへリンクしても、日本語の法人ディレクトリ→日本の会社→英語圏の漫画解説サイト、という連鎖は話題の関連性が弱く、効果は限定的だと。

**それに対して、こう返された。**

> 順位以前の問題で価値が認められてなさすぎるから、関係なくてもある程度効くのでは？

この指摘が正しかった。そして調べたら、指摘の線で明確な穴が見つかった。

## 順位の話と、存在認知の話は別

関連性の重み付けは**順位**に効くものだ。「このクエリに対してどのページを上位に出すか」の判断で使われる。

だが 133/151 が未認識という状態は、順位を争う段階にすらいない。ここで Google が答えようとしている問いは違う。

> **これは実在する主体か？**

この問いに対しては、話題の関連性はほとんど関係ない。必要なのは**裏付け**だ。しかも今回のケースでは、法人サイトと事業サイトは**同一主体**だった。一般的な「1ホップ経由の減衰」の話ではなく、エンティティの補強にあたる。

私は2つの話を混ぜていた。

## 実際に何が足りなかったか

指摘を受けて構造化データを確認した。

**法人サイト側:**

```json
{
  "@type": "Organization",
  "name": "Faanau, inc.",
  "legalName": "株式会社ファーナウ",
  "identifier": {
    "@type": "PropertyValue",
    "propertyID": "JP-CorporateNumber",
    "value": "7020001112364"
  }
}
```

法人番号まで入っている。**しかし `sameAs` が無い。** 事業サイトへの言及が構造化データ上ゼロだった。

**事業サイト側:**

トップページに構造化データが**1つも無かった**。記事ページには `Article` が出ていたが、`publisher` はこうだった。

```json
"publisher": { "@type": "Organization", "name": "Faanau, inc." }
```

**名前だけ。** URLも識別子も無い。

これでは検索エンジンから見て、2つのドメインは無関係だ。`<a href>` は張ってあるが、**リンクは「誰が運営しているか」を何も主張しない**。

```
faanau.co.jp   法人番号あり・実在の裏付けあり
      ↕
     （構造化データ上の接続なし）
      ↕
jpn.fan        運営主体の宣言なし
```

## 法人番号が効く理由

直した内容自体は単純だが、**何を載せるかの選択**が要点だった。

法人サイト側に `sameAs` と `owns` を足す。

```json
"sameAs": [
  "https://jpn.fan",
  "https://github.com/faanau",
  "https://www.npmjs.com/~faanau"
],
"owns": [
  {
    "@type": "WebSite",
    "name": "jpn.fan",
    "url": "https://jpn.fan"
  }
]
```

事業サイト側には `Organization` と `WebSite` を置き、記事の `publisher` を名前だけから完全な形にする。**両方に同じ法人番号を載せる。**

```json
"identifier": {
  "@type": "PropertyValue",
  "propertyID": "JP-CorporateNumber",
  "value": "7020001112364"
}
```

ここが本質だと思う。

`sameAs` は**自己申告**だ。誰でも書ける。「私はあのサイトの運営者です」と主張しているだけで、それ自体に検証手段は無い。

法人番号は違う。**国税庁の法人番号公表サイトで誰でも照合できる。** 法人名、所在地、番号が一致するかを外部から確認できる。

```
自己申告  「この2つは同じ主体です」
     ↓
検証可能  「その法人番号は実在し、この法人名と一致する」
```

**主張が、確認できる主張になる。** 偽装しようとすれば実在の法人の番号を騙ることになり、それは名称や所在地との突き合わせで破綻する。

日本の会社なら法人番号、他国なら VAT番号や company registration number が同じ役割を果たす。schema.org の `PropertyValue` は `propertyID` で識別子の種類を明示できるので、どの国の制度でも表現できる。

## 実装

`identifier` は複数持てるので、必要なら並べればいい。

```json
"identifier": [
  { "@type": "PropertyValue", "propertyID": "JP-CorporateNumber", "value": "..." },
  { "@type": "PropertyValue", "propertyID": "VAT", "value": "..." }
]
```

事業サイトが複数あるなら `owns` に並べる。逆向きに、各事業サイトの `publisher` から法人サイトを指す。**双方向にしておく。**

定数として1箇所にまとめて、記事テンプレートから参照する形にした。名前だけを直書きしていると、直すときに全テンプレートを触ることになる。

```ts
export const PUBLISHER = {
  '@type': 'Organization',
  name: 'Faanau, inc.',
  legalName: '株式会社ファーナウ',
  url: 'https://faanau.co.jp',
  identifier: { /* 法人番号 */ },
  sameAs: [ /* 全プロパティ */ ],
} as const;
```

リポジトリが分かれている場合は**両方に同じ定数を置く**。DRYではないが、片方だけ更新される事故の方が痛い。コメントに「もう一方と同期すること」と書いておく。

## 検証

デプロイ後、3ドメイン横断で同じ番号が出ているかを機械的に確認した。

```python
def dig(d):
    """入れ子のどこにあっても法人番号を見つける"""
    if isinstance(d, dict):
        if d.get('propertyID') == 'JP-CorporateNumber':
            return d.get('value')
        for v in d.values():
            if (r := dig(v)): return r
    if isinstance(d, list):
        for v in d:
            if (r := dig(v)): return r
```

```
faanau.co.jp/                              法人番号 7020001112364
jpn.fan/                                   法人番号 7020001112364
jpn.fan/c/luffy/pitfalls/nakama-five-ways/ 法人番号 7020001112364
```

`publisher` の中に入っていても拾えるように、再帰で探している。**「どこかに書いた」ではなく「実際に出力されている」を確認する**のが要点で、私はこの確認の途中で自分の誤診も見つけた（後述）。

## 途中で1つ誤診した

調査中、「事業サイトの構造化データが全ページで壊れている」と報告した。**これは誤りだった。**

live のURLをいくつか叩いて全部 0 ブロックだったので、そう結論した。実際にはビルド成果物を調べると **458ファイル中405に構造化データがあった**。私が叩いたURLが、たまたま全部 schema を持たないページ（一覧ページ、キャラのトップ、about系）だっただけだ。

**サンプルの偏りで「全部壊れている」と判断しかけた。** 全数を見れば5分で分かることだった。

本当の穴は、最初に挙げた3点だけだった。

## まとめ

- **「順位が上がるか」と「実在が認められるか」は別の問題。** 前者では話題の関連性が効くが、後者では関連性の薄い裏付けでも働く
- 新しいドメインで、まだほとんど認識されていない段階なら、**問われているのは後者**
- `<a href>` は誰が運営しているかを何も主張しない。**構造化データで明示する**
- `sameAs` は自己申告。**外部の公的データベースと照合できる識別子**（法人番号など）を載せると、主張が検証可能になる
- 双方向にする。定数は1箇所にまとめる。リポジトリが分かれるなら同期を明記
- **「書いた」ではなく「出力されている」を確認する。** サンプルではなく全数で

そして、自分の説明が雑だったときに指摘してくれる相手がいると助かる。今回は指摘の方が正しかった。

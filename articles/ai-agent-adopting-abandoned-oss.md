週35万DLされながら8年間更新の止まっていた npm パッケージを、AI エージェントに引き取らせた。調査からフォーク、バグ修正、CI 構築、npm 公開、上流への PR まで、実作業のほとんどをエージェントが進めた。

結果としてはうまくいった。だが「AIにやらせたら全部できました」という話ではない。**人間が介入しなければ失敗していた箇所がいくつもある。** そこを書いておく方が、たぶん役に立つ。

## 何をやったか

対象は日本語形態素解析器の JS 実装。Open Issue が15件あり、Firefox で動かない、外部URLから辞書を読めない、といった報告が並んでいた。

エージェントがやったこと:

- 全 Issue と PR の棚卸し、再現確認
- 死んでいたツールチェーンの刷新（gulp3 → mocha + esbuild）
- バグ修正3件と回帰テストの追加（52 → 66テスト）
- 8年前の依存2つの除去（バンドル 308KB → 69KB）
- ESM と型定義の追加、CI 構築、npm 公開
- 上流への PR 3本

## エージェントが強かったところ

### 全数調査

いちばん効いたのはこれだった。

Issue が15件あると「15件のバグがある」と思う。エージェントは全部を実際に再現しにいき、こういう結果を出した。

- **#37 / #39 / #43 は同一原因**（`path.join` が `https://` を `https:/` に潰す）
- **#36 は再現しない**（報告時から修正済み、あるいは誤報）
- **#53 はそもそも別リポジトリの問題**

15件が実質数件になった。人間は「たぶん似た話だろう」で止めがちだが、**全部叩くのを厭わない**のは明確な強みだった。

### テーブル駆動テストの網羅

リダイレクトの検証で、エージェントは「リダイレクト先を自分自身に食わせ直してホップ数を数える」テストを書いた。

```js
function resolve(url, max = 5) {
  let current = url, hops = 0;
  for (;;) {
    const out = handler(makeEvent(current));
    if (out.statusCode === 301) {
      hops += 1;
      if (hops > max) throw new Error(`redirect loop from ${url}`);
      current = out.headers.location.value;
      continue;
    }
    return { hops, final: current };
  }
}
```

**「1ホップで着く」という仕様がテストで表現できる形**になった。この手の「網羅的で退屈な検証」は、書かせると素直に書く。

### 記録

コミットメッセージや設計ドキュメントに、**なぜそうしたか**が残る。人間が急いでいるときに最初に省略する部分が、省略されない。

## 人間が介入しなければ失敗していたところ

ここからが本題。

### 1. サンプルの偏りで「全部壊れている」と誤診した

構造化データが出ているかを調べるとき、エージェントは live のURLをいくつか叩いて全部 0 だったので「全ページで壊れている」と報告した。

**実際にはビルド成果物 458 ファイル中 405 に出ていた。** 叩いたURLがたまたま全部、構造化データを持たない種類のページだっただけだ。

その後で全数を数えて誤りに気づき、訂正した。だが**訂正しなければ、存在しないバグの修正に時間を使っていた**。

教訓としては、AI 特有というより一般的なものだ。**サンプルで全体を判断しない。** ただしエージェントは「数件見て結論を出す」を高速にやるので、間違った結論にも高速に到達する。

### 2. `git add -A` で他人の作業を巻き込んだ

エージェントが変更をコミットするとき `git add -A` を使い、**同じリポジトリで並行して進んでいた別作業を丸ごと巻き込んだ**。コミットメッセージは自分の変更しか説明していない。

気づいて、コミットを解いて、内容を確認した上で「これは複数の作業を含んでいる」と明記したメッセージで作り直した。

これは**共有リポジトリで作業させるときの典型的な事故**だと思う。エージェントは自分が触ったファイルを正確に把握しているのに、`-A` で全部拾ってしまう。

対策は単純で、**変更したファイルを明示的に列挙させる**。

### 3. 自分の書いた検証に2回止められた

コメント除去スクリプトを書かせたとき、安全のための検査をエージェント自身が追加した。それが**正しいコードを誤検知で拒否した**。

1回目：文字列リテラル中の `//` を「コメント開始」と誤検知。原因は `https://`。
2回目：`` ` `` の存在をテンプレートリテラルと誤検知。原因は**コメント内の説明文**にバッククォートが使われていたこと。

どちらも自分で気づいて直したが、**検査を厳しくしすぎて正しいものを弾く**のはよくやる。「安全側に倒す」を機械的にやると、動かないものが出来上がる。

### 4. 「テストを書いた」で終わりかける

回帰テストを追加したとき、**それが実際に不具合を検出するかは別の話**だ。

修正を一時的に戻して、テストが本当に落ちることを確認した。4件が落ちた。これをやらないと「通っているテスト」が増えるだけで、何も守られていない可能性がある。

これは指示して初めてやった工程だった。**「テストを書け」ではなく「そのテストが落ちることを確認しろ」まで言う必要がある。**

### 5. 破壊的な操作の判断

上流には「依存を減らすために辞書ファイルを非圧縮で配る」という提案 PR があった。エージェントはこれを採らず、`DecompressionStream` で形式を保ったまま依存だけ消す方を選んだ。

これは良い判断だったが、**選択肢を並べて理由を書かせた上で、人間が確認している**。放っておいて破壊的な方を選んでいたら、既存利用者が壊れていた。

「10万人が使っているかもしれない」という感覚は、指示に含めておかないと出てこない。

### 6. 外向きの行為

npm publish、GitHub の PR 作成、本番デプロイ。これらは**取り消せないか、取り消しに手間がかかる**。

エージェントは毎回確認を取る設計にしていたが、そうでなければ:

- 検証していないパッケージが publish される（npm の unpublish は事実上不可）
- 他人のリポジトリに未完成の PR が立つ

**不可逆な操作の手前で必ず止まる**ようにしておくのは、必須だと思う。

## 分業のかたち

うまくいった配分はこうだった。

| | 担当 |
|---|---|
| 全数調査・再現確認 | エージェント |
| 網羅的なテスト | エージェント |
| 依存の棚卸し・機械的な移行 | エージェント |
| 記録・ドキュメント | エージェント |
| **サンプルの妥当性判断** | 人間 |
| **破壊的変更の可否** | 人間 |
| **外向きの行為の承認** | 人間 |
| **「その検証は本当に効くのか」** | 人間 |

言い換えると、**「作業」は任せられて、「判断」は任せられなかった**。

そして判断のうち最も重要だったのは、**エージェントが出した結論を疑うこと**だった。誤診1件を訂正したのが、この作業でいちばん価値のある介入だった気がする。

## 速さについて

正直に書くと、**速い**。ツールチェーンの刷新、テストの追加、依存の除去、CI 構築を1日で通した。人間だけなら数日から1週間かかる規模だと思う。

ただし速さの内訳は「タイピングが速い」ではなく、**「退屈な確認を厭わない」**ことによる。15件のIssueを全部再現する、145本のURLを全部叩く、といった作業を省略しないので、結果的に判断が早い。

逆に言えば、**省略しない代わりに、間違った方向にも全速力で進む**。だから止める側が要る。

## まとめ

- AI エージェントは**全数調査と網羅的な検証**が強い。人間が「たぶん同じ」で省略する部分を省略しない
- **サンプルで全体を判断する誤りは、速く起きる**。結論を疑う人間が要る
- 共有リポジトリでは `git add -A` 相当の操作に注意。**変更ファイルを明示させる**
- 「テストを書け」では足りない。**「そのテストが落ちることを確認しろ」**まで言う
- 破壊的変更と外向きの行為は、**選択肢と理由を出させて人間が決める**
- 任せられるのは作業、任せられないのは判断。特に**エージェント自身の結論の妥当性**

この記事も、作業ログから起こしている。失敗した箇所は隠さずに書いた方が、次に同じことをやる人の役に立つと思う。

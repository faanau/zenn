AI に下書きさせた記事を150本ほど運用している。日本語の原文と英訳を突き合わせて解説するもので、事実の密度が高い。

始める前に想像していたボトルネックは「量を作ること」だった。実際に詰まったのは全部**その後ろ**だった。

**生成は安い。検証が高い。** そして検証を人手でやる限り、量を増やした分だけ人手が要る。だから**検証を仕組みにしないと、AIで量を作る意味がほとんど無い。**

この記事は、そこで実装した3つの検証と、途中で気づいた1つの原則の話。

## 前提：何が危険か

AI 生成コンテンツの品質問題は、ふつう「ハルシネーション」と一括りにされる。だが実務で扱うときは、**発見のしやすさで分けた方がいい**。

| | 例 | 発見しやすさ |
|---|---|---|
| **無い** | 出典が書かれていない | 見れば分かる |
| **形が違う** | 引用が本文と一致しない | 機械で分かる |
| **間違っている** | 読みが違う、事実が違う | **見ても分からない** |

上2つは仕組みで潰せる。問題は3つ目で、**一見して自然に見える**。しかも間違った情報は記事本文からPDF、動画台本へと伝播する。

だから検証の設計は、**「見ても分からないもの」をどう機械にかけるか**の話になる。

## 検証1：機械で読みを疑う

日本語の原文にふりがなが付いている。AI が振ったものだ。

形態素解析器を入れるとき、最初は「足りないふりがなを生成しよう」と考えた。データを見たら**全部すでに付いていた**。生成する対象が無い。

では解析器は不要かというと逆で、**振られたふりがなを疑う**のに使えた。

```js
// ruby マークアップから読みを再構成
const claimed = kanaOnly(readingFromFurigana(entry.furigana));
// 解析器が原文から導く読み
const derived = kanaOnly(
  tokenizer.tokenize(entry.jp).map(t => t.reading || t.surface_form).join('')
);
```

食い違いが12件出た。

## 検証器も間違う

ここが本題だ。**12件すべて、辞書の方が間違っていた。**

| 語 | AI/著者 | 辞書(IPADIC) |
|---|---|---|
| 錆兎 | さびと | さび**うさぎ** |
| 鬼殺隊 | きさつたい | **おにやたい** |
| 拾壱 | じゅういち | **じついち** |
| 宝物 | たからもの | **ほうもつ** |
| 七日間 | なのかかん | **なにちかん** |

固有名詞は当然として、`鬼殺隊 → おにやたい` のような分解由来の誤りや、`宝物 → ほうもつ`（作品中は「たからもの」）のような文脈依存の読みが混ざる。

**もし「解析器の読みで上書きする」を実装していたら、正しい読みが12箇所壊れていた。** しかも壊れたことは見て分からない。

一般化するとこうなる。

> **生成器を検証器として使うとき、検証器の出力もまた検証されていない。**

AI の出力を別の AI で検証する構成でも同じことが起きる。検証器が「間違っている」と言ったからといって、生成器が間違っているとは限らない。

だから設計はこうした。

```
✗ 検証器の出力で上書きする
✓ 食い違いを報告し、人間が答える
✓ 答えた内容を理由付きで記録し、二度と聞かれないようにする
```

## 検証3：判断を記録して、繰り返し聞かれないようにする

「人間が答える」だけだと、実行のたびに同じ12件を見せられる。そのうち誰も読まなくなる。

なので**レビュー済みの判断を、理由とともに保存する**。

```json
{
  "no-place-in-the-corps":
    "鬼殺隊 read きさつたい. IPADIC's おにやたい is a decomposition
     artifact. This is the exact kisatsutai ⇄ oni-koroshi-tai confusion
     the project's review notes call out.",

  "this-hat-is-my-treasure":
    "宝物 read たからもの, the kun-reading the character uses.
     IPADIC prefers ほうもつ, which is the museum-artifact sense."
}
```

要点は、**「無視リスト」にしないこと**。値に「なぜそちらが正しいのか」を書く。

こうしておくと:

- 後から**判断そのものを再検討できる**
- エントリを消せば、次の実行でまた問いとして浮上する
- 新しく参加した人が、なぜ例外なのかを理解できる

結果、日常の実行はこうなる。

```
$ npm run check:readings
readings — 55 checked, 4 with no ruby, 12 reviewed
  every authored reading agrees with the analyzer
```

**新しい食い違いだけが声を上げる。** これで初めて、CI に入れられる状態になる。

## 検証2：形式は機械で強制する

「見れば分かる」種類の欠陥は、そもそも人間に見せない。ビルドで落とす。

うちで必須にしているもの:

- **一次ソースの引用**（巻・ページ。版を明示する）
- **画像の出典と権利表記**
- **語数の下限**

最後のものは、AI 下書き特有の事情がある。**AI は「それらしい短文」を無限に作れる**。放っておくと、体裁は整っているが中身が無いページが量産される。

実際、145ページ中37ページが300語未満で、うち27ページは**テンプレートのプレースホルダをそのまま本番に出していた**。

```
Stub page — the production article includes first-appearance citation,
related terms, and panel references.
```

個別に直しても、次のバッチでまた出る。**ビルド時のゲートにするしかない。**

```ts
export function isThin(entry: unknown): boolean {
  const data = (entry as any)?.data ?? entry;
  return proseWords(data) < CONTENT_DEPTH_MIN;
}
```

閾値未満は `noindex, follow` を出し、sitemap から外す。**ページは残る**ので404にはならず、書き上がれば自動で戻る。

語数のカウントは**散文だけ**にする。出典リストやメタデータを数えると、AI が引用を10件足して閾値を超えてくる。

```ts
const NON_PROSE = new Set([
  'slug', 'characterSlug', 'sources', 'references', 'tags', 'aiModel',
]);
```

**ゲートは、迂回路を先に塞いでから入れる。**

## 検証4：重複を機械で見つける

AI に大量に書かせると、**同じことを別の切り口で書いたページ**が増える。人間なら「これ前も書いたな」と気づくが、1本ずつ生成していると気づかない。

3種類に分けて検出した。

- **同じ語・違うセクション** — 37語のスタブが2000語の記事を押さえつけていた
- **同じ原文・違うスラッグ** — 6組。これは事故ではなく**設計の問題**で、キャラを追加するたび再生産される
- **同じ語・違うキャラ** — たいてい正常だが、互いのコピーになっていないか確認が要る

そして**書き始める前に聞ける**ようにした。

```
$ node scripts/check/keyword-overlap.mjs --term dattebayo

Pre-flight: "dattebayo"
  2 existing entr(ies) already touch this term:
    2003w  /c/naruto/pitfalls/dattebayo/
      37w  /c/naruto/glossary/dattebayo/
```

生成の前に「その題材は既に誰かが扱っているか」を機械に聞く。**AI は聞かないと重複を作る。**

## 開示について

AI 下書きであることを読者に開示するかどうかは、技術ではなく方針の問題だ。ここでは答えを出さないが、設計上こう考えている。

**開示すべきかどうかより、「開示したときに耐えられる作り方をしているか」の方が先**だと思う。

- 一次ソースが引用されている
- 読みが機械で検証されている
- 誰が監修しているかが明示されている

これが揃っていれば、開示は減点にならない。揃っていないなら、開示するかどうかに関わらず問題がある。

## まとめ

- **生成は安い。検証が高い。** 人手で検証する限り、AIで量を作る意味は薄い
- 欠陥は「発見しやすさ」で分ける。**「見ても分からない」ものだけが機械の出番**
- **検証器も間違う。** 検証器の出力で自動修正してはいけない。食い違いは「問い」であって「判定」ではない
- 人間の判断は**理由とともに記録**する。無視リストにしない
- 形式的な要件はビルドで強制する。ただし**迂回路を先に塞ぐ**
- AI は聞かないと重複を作る。**生成前に聞ける仕組み**を用意する

実装したものはどれも100行前後の素朴なスクリプトで、難しいことは何もしていない。難しかったのは、**「検証器を信じすぎない」という一点**を設計に落とすことだった。

最初に書きかけた自動修正を捨てられたのは、たまたま12件を目視した結果、全部が辞書の誤りだったからだ。**確認せずに実装していたら、静かに壊していた。**

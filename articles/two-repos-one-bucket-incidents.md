1つのサイトを2つのリポジトリから配信している。歴史的経緯で、古い方（v1）と新しい方（v2）が別々に存在し、**同じ S3 バケットに書き込む**。CloudFront も1つ。

この構成で、1日のうちに3件やらかした。どれも「片方だけ見ていると正しく見える」種類の事故だったので、記録しておく。

## 事故1：`--delete` が相手のファイルを消す

`aws s3 sync --delete` は、同期元に無いオブジェクトを削除する。バケットを共有していると、**相手が置いたファイルは「同期元に無い」**。

これは分かっていたので、共有プレフィックスは除外していた。

```bash
aws s3 sync ./dist "s3://$BUCKET/" --delete \
  --exclude "_assets/*" \
  --exclude "fonts/*" \
  --exclude "themes/*"
```

3つ除外してあるから安全、のつもりだった。**実際に本番と突き合わせたら4つ足りなかった。**

```
/w/*                335 ファイル   v2 が生成、v1 は1つも生成しない
/manga-panels/*     1,009 中 965 が v2 のもの
/concept/*, /preview/*             v2 のみ
about/index.html, favicon.svg      v2 がこの名前で生成している
```

**このまま実行していたら 1,302 オブジェクトが消えていた。**

厄介なのは `/about/` で、これは**所有が分かれている**。

```
v1 が持つ:  about/aine/     about/methodology/
v2 が持つ:  about/index.html  about/community/
```

プレフィックスごと除外すると v1 自身のページが更新できなくなる。かといって除外しないと v2 のファイルが消える。**ディレクトリ単位で所有権が決まらない**構造になっていた。

暫定として v2 のファイル名を個別に除外したが、これは対症療法だ。所有の分割そのものを決め直すべき問題として残っている。

### 教訓

`--delete` を共有バケットで使うなら、**除外リストが正しいことを毎回確認する**しかない。より正確には、こう考えた方がいい。

> 除外リストは「相手が今どこに何を置いているか」のスナップショットであり、相手が新しいプレフィックスを使い始めた瞬間に古くなる。

安全側に倒すなら、**`--delete` を使わない（add-only）** のが正しい。削除は明示的に `aws s3 rm --recursive <特定prefix>` でやる。実際、共有アセットは既にそうしていた。パネル画像も同じ契約に寄せた。

**実行前に必ず差分を出す。** `--dryrun` で何が消えるかを見て、想定と一致してから実行する。

```bash
aws s3 sync ./dist "s3://$BUCKET/" --delete --dryrun | grep '^delete:' | wc -l
```

## 事故2：無害な `catch` がデータを消した

デプロイ手順にこういうスクリプトがある。sitemap のインデックスは両リポジトリで共有していて、片方が自分の分だけで上書きすると相手が消える。だから**現在のインデックスを読んで、union してから書く**。

```js
let liveXml = '';
try {
  const res = await fetch(LIVE_URL, { cache: 'no-store' });
  if (res.ok) liveXml = await res.text();
} catch {
  // Live index may not exist yet (first-ever deploy) — proceed with built only.
}
```

コメントの通り、初回デプロイでは存在しないので、握りつぶして進む。**一見まっとうに見える。**

問題は `LIVE_URL` が CDN 経由だったことだ。そして**このスクリプトは、同じデプロイ手順が invalidation を打った直後に走る**。

キャッシュミスは正常な事象だ。そして

```
読めなかった  →  liveXml = ''  →  「何も無い」  →  自分の分だけで上書き
```

その日、これが実際に起きた。v1 が自分の dist からインデックスを作り直し、**4キャラ中3キャラが live のインデックスから消えた**。

エラーは出ない。デプロイは成功する。**壊れたことに気づく手段が無い。**

### 教訓

「読めなかった」と「無かった」を同じ値で表現してはいけない。この2つは意味が正反対で、後者だけが「ゼロから作り直してよい」を意味する。

修正はこうした。

```js
async function readLiveIndex() {
  // 1. まずオリジン（S3）から読む。CDN を経由しない
  const bucket = process.env.S3_BUCKET;
  if (bucket) {
    const r = spawnSync('aws', ['s3', 'cp', `s3://${bucket}/sitemap-index.xml`, '-']);
    if (r.status === 0 && r.stdout.includes('<sitemapindex>')) {
      return { xml: r.stdout, source: 's3' };
    }
  }
  // 2. フォールバックで CDN
  ...
  return { xml: '', source: null };   // ← 読めなかったことを区別できる形で返す
}

const { xml, source } = await readLiveIndex();
if (!source) {
  if (process.env.ALLOW_MISSING_INDEX === '1') {
    console.warn('WARNING: no existing index; building from scratch.');
  } else {
    console.error('ABORT: could not read the existing sitemap index.');
    console.error('  Merging without it would drop everything this repo does not build.');
    process.exit(1);
  }
}
```

要点は3つ。

1. **読み書きするデータは、キャッシュ層を経由せずオリジンから読む。** CDN は配信のためのもので、状態の読み戻しには使わない
2. **「無かった」を許すのは、明示的に宣言されたときだけ。** 既定は fatal
3. **失敗したときに何が起きるかをエラーメッセージに書く。** 「マージできません」ではなく「このリポジトリが生成しないものが全部消えます」と書く

### 余談：これは私の書いたコードだった

この `catch` を書いたのは私だ。書いた時点では「初回デプロイで落ちないように」という正当な意図があり、コメントもそう書いてある。

**善意の握りつぶしが、いちばん見つけにくい。** エラーを無視しているのではなく、想定された正常系として扱っているので、レビューでも通ってしまう。

## 事故3：ガードが正しいビルドを全部拒否した

デプロイ手順にビルド成果物の検査がある。

```js
// dev 用プレフィックスが本番に漏れていないか
grep -rlE 'href="/c/{slug}/' dist/
// → 見つかったら deploy を中止
```

サイト構成を変えて、**`/c/{slug}/` が本番の正しい形になった**。ガードは仕様変更に追随していないので、**正しいビルドを毎回拒否する**ようになった。

これ自体は「デプロイできない」だけなので害は小さい。だが厄介なのは、**このガードを外して通したくなる**ことだ。「今は正しいはずだから `--no-verify` で」とやると、次に本物の漏れが起きたとき止まらない。

ガードは外すのではなく**反転**させた。今は逆に、退役したサブドメインURLが残っていないかを見ている。

### 教訓

**「何を禁止しているか」は、仕様変更で意味が変わる。** ガードを書くときは、禁止対象を仕様の言葉で書いておくと気づきやすい。

```js
// ✗ 「/c/{slug}/ を含んではいけない」          ← 何故かが消えている
// ○ 「dev専用のリンク形式が本番に漏れてはいけない」← 仕様が変わったら書き換えると分かる
```

## そもそも、なぜ1バケットなのか

ここまで読んで「分ければいいのでは」と思うはずで、正しい。

理由は CloudFront と証明書と CloudFront Function を共有していることで、分割するとエッジの設定を二重管理することになる。今のところ、事故のコストより設定の複雑化のコストの方が高いと判断している。

ただしその判断が成立するのは、**契約が明示されている場合だけ**だ。今回の3件はどれも「契約が暗黙だった」ことが原因だった。

- どのプレフィックスを誰が所有するのか
- 共有するものは add-only か
- 相手の状態を読み戻すとき、どこから読むのか

これを書いたドキュメントが無いまま2つのリポジトリを走らせると、**片方だけを見る限りどちらのコードも正しく見える**。レビューでも見つからない。

## まとめ

- 共有バケットで `--delete` を使うなら、除外リストは**毎回本番と突き合わせる**。安全側は add-only
- **「読めなかった」と「無かった」を同じ値にしない。** 特にキャッシュ層越しに読むときは、ミスが正常系に紛れる
- 状態の読み戻しは**オリジンから**。CDN は配信専用
- ガードは仕様変更で意味が変わる。**外さずに反転させる**
- 暗黙の契約は、レビューでは見つからない。**書く**

3件とも「片方のリポジトリだけを見ると正しい」形をしていた。共有インフラのバグは、だいたいそういう顔をしている。
